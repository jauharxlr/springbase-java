# Software Requirements Specification (SRS)
## Project Name: SupaSpring (Base Clone)
**Version:** 1.1 (Ownership-Based Security)  
**Date:** 2026-02-06

---

### 1. Introduction
This document defines the technical specifications for **SupaSpring**, a Spring Boot backend platform. This version focuses on a streamlined "Automatic Ownership" security model to replace complex RBAC, making it accessible for users with zero backend knowledge.

---

### 2. Functional Requirements

#### 2.1 Authentication & Multi-tenancy
*   **2.1.1 Project Isolation**: Each user project has a unique `project_ref`. All data (tables, users) is logically partitioned by this ID.
*   **2.1.2 Auth Providers**: Support for Email/Password and OAuth2 (Google/GitHub) using Spring Security.
*   **2.1.3 Session Management**: JWT-based authentication. JWT Claims MUST include:
    *   `sub`: User UUID
    *   `project_ref`: The project this user belongs to
    *   `role`: Either `anon`, `authenticated`, or `service_role`.

#### 2.2 Dynamic Database Engine (Auto-CRUD)
*   **2.2.1 Schema Definition API**:
    *   Endpoints to create/alter tables via JSON payloads.
    *   SupaSpring maintains a internal metadata catalog to track which columns exist in user-defined tables.
*   **2.2.2 Automatic REST Endpoints**:
    *   `GET /rest/v1/{table}`: Auto-generates SQL based on project metadata.
    *   Supports PostgREST-style filters: `?name=eq.Alice&age=gt.20`.
    *   Standard JSON responses for all CRUD operations.

#### 2.3 Automatic Ownership Security (The "Simple-Power" Model)
This replaces complex RLS/RBAC with a convention-based system.

*   **2.3.1 The Three-Tier Key System**:
    *   **Anon Key**: For public access. Limited by "Public Read" toggles.
    *   **User Key (JWT)**: For logged-in users. Limited by ownership.
    *   **Service Role Key**: Super-user bypass. No filters applied.
*   **2.3.2 Ownership Injection Logic**:
    *   If the engine detects a column named `user_id` or `owner_id` in the target table:
        *   **For `authenticated` role**: The engine MUST automatically append `AND user_id = auth.uid()` to every `SELECT`, `UPDATE`, and `DELETE` query.
        *   **For `INSERT`**: The engine MUST automatically set the `user_id` column to the current user's UUID from the JWT.
*   **2.3.3 Public Read Toggle**:
    *   Metadata flag per table: `is_public_read`.
    *   If `true`, queries with the `anon` key are allowed for `SELECT` only.
    *   If `false`, `anon` keys receive a `403 Forbidden`.

#### 2.4 API Documentation & Discovery
*   **2.4.1 Dynamic OpenAPI Generation**: SupaSpring must scan the metadata for a project and generate a customized OpenAPI 3.0 JSON/YAML.
*   **2.4.2 Swagger UI**: Expose a hosted Swagger UI at `/docs/{project_ref}` for interactive API testing.

#### 2.5 AI-Assisted Script & Migration Support (The "AI-First" Workflow)
To facilitate seamless interaction with AI coding assistants, SupaSpring provides dedicated endpoints for schema and logic injection.

*   **2.5.1 The "SupaShell" SQL Editor**:
    *   Endpoint: `POST /admin/v1/sql`. 
    *   Requirement: Accepts raw SQL strings (for DDL or DML).
    *   Implementation: Executes via JDBC with a `service_role` security context. This allows AI assistants to generate and execute standard SQL migrations directly against the project.
*   **2.5.2 JSON-to-DDL Converter**:
    *   Endpoint: `POST /admin/v1/schema/apply`. 
    *   Requirement: Accepts a JSON representation of a database schema (generated by an AI).
    *   Action: The engine automatically translates this JSON into `CREATE TABLE`, `ALTER TABLE`, or `ADD CONSTRAINT` statements and updates the metadata catalog.
*   **2.5.3 Dynamic Script Execution (Optional/Future)**:
    *   Support for injecting small logic snippets (e.g., in Groovy or JavaScript) to run as custom API hooks, enabling AI to write "backend logic" on the fly.

### 3. Technical Requirements

#### 3.1 Backend Stack (MVP Version)
*   **Framework**: Spring Boot 3.4+ (Java 21).
*   **Database (MVP)**: **H2 (In-Memory)** with **PostgreSQL Compatibility Mode**. This allows for zero-dependency local testing while remaining compatible with a production PostgreSQL instance.
*   **Cache (MVP)**: **Caffeine (In-Memory)** for project metadata caching.
*   **Query Engine**: Custom JDBC implementation using `NamedParameterJdbcTemplate` or **JOOQ** for dynamic SQL construction and JSON aggregation.
*   **Routing**: Spring Cloud Gateway for `apikey` validation and role extraction.

#### 3.2 Database Strategy
*   **Multi-tenancy**: Shared PostgreSQL instance. Every user table is created with a `project_ref` column (Tenant Discriminator) to ensure data never leaks between projects.

---

### 4. Simplified User Workflow (No-Code Friendly)
1.  **Create Table**: User uses the UI to create a table "Tasks".
2.  **Enable Security**: User adds a column named `user_id`. SupaSpring now handles all security automatically.
3.  **Use API**: User copies the auto-generated URL and starts building their frontend.

---

### 5. Non-Functional Requirements
*   **Performance**: Query overhead for ownership injection must be < 5ms.
*   **Safety**: All dynamic SQL MUST use parameterized queries.
*   **Ease of Use**: The "Ownership" model must be the default behavior for all new tables.
